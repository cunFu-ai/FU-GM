# FU-GM 提示词缓存优化报告

日期：2026-08-06，2026-08-07 追加跨消息前缀优化

## 结论

三模型长测中的缓存都在工作，但原始“缓存读取 token / 全部提示词 token”只能表示总体成本覆盖率，不能直接解释一次调用是否缓存失败。供应商未返回缓存明细时，旧统计会把结果混入分母，却无法区分冷启动、已命中但未报告、请求太小不具备缓存资格三种情况。

本轮已将 FU-GM 的提示词缓存改为两层稳定前缀：

1. 系统层按 GM 阶段和模式划分缓存族，例如初始化、第零章、场景、冲突、工具后续和心跳。
2. 回合层把当前玩家消息、近期对话和本轮稳定上下文放在用户消息前半段；易变化的权威状态、工具目录和工具回执位于缓存断点之后。

针对同一稳定回合、仅改变后半段动态状态的真实 ai-pixel 请求，第二和第三次调用均读取了 `5,888 / 6,497` 个提示词 token，稳定部分读取率约为 `90.6%`。本次小样本中的延迟由首次约 `10.1s` 降至约 `5.0s` 和 `5.7s`；这只能证明缓存路径有效，不能视为供应商延迟的长期保证。

## 原始数据解释

| 模型 | 缓存命中调用 | 原始读取比例 | 判断 |
| --- | ---: | ---: | --- |
| Luna | 73/73 | 32.28% | 已报告的调用全部命中；大量动态状态和原先未标记的语义审计降低总体 token 覆盖率。 |
| Terra | 71/71 | 20.94% | 已报告的调用全部命中；语义落地审计占用大量提示词且原先不具备缓存标记，因此总体比例最低。 |
| DeepSeek | 121/128 | 47.55% | 7 次已知未命中并非主缓存反复失效。 |

DeepSeek 的 7 次已知未命中由以下调用组成：

- 2 次新阶段或新前缀的首次冷启动调用。
- 1 次一次性的场次契约可达性审查。
- 4 次仅约 285 至 510 token 的解析重试，小于供应商通常可缓存的前缀规模。

因此，不能据此判断主 GM 提示词前缀不稳定。真正的问题是缓存覆盖范围和可观测性不足，而不是三个模型都在频繁重建同一个缓存。

## 已完成改造

- `prompt_cache.py` 支持系统消息和用户消息分别设置缓存断点，同时保持现有两消息调用格式，避免破坏测试客户端及兼容端点。
- `gm_tool_agent.py` 使用按阶段拆分的缓存族，并在工具后续循环中缓存本轮不变的玩家消息、近期聊天及请求上下文。
- `gm_reply_grounding_verifier.py` 为公开回复审计和工具写入审计建立独立缓存族；动态候选回复或工具参数置于断点之后。
- `llm_client.py` 将缓存调用分成“具备资格”“供应商返回用量”“确认命中”“确认未命中”和“未返回明细”，并按缓存族、操作类型统计 token、前缀变体及 P50/P95 延迟。
- 长测报告会保存完整缓存遥测，模型矩阵不再只保留一个总读取比例。
- 仪表盘增加总体读取率、具备资格调用读取率、已报告调用读取率，以及缓存族和操作类型明细。

## 新统计口径

- **总体读取率**：缓存读取 token / 全部提示词 token。用于估算整体成本覆盖率。
- **具备资格调用读取率**：缓存读取 token / 已标记可缓存调用的提示词 token。用于判断缓存设计覆盖度。
- **已报告调用读取率**：缓存读取 token / 供应商明确返回缓存明细的提示词 token。用于分析已知结果。
- **确认未命中**：供应商返回缓存明细且读取 token 为零。
- **未知调用**：供应商未返回缓存明细。未知不再被标记为缓存失败。

缓存族明细还会记录 cache key、基础前缀和最长前缀的变体数量。若某个逻辑阶段突然产生大量前缀变体，可以直接定位是哪类提示词发生了无谓变化。

## 验证

- 完整测试：`2023 passed in 18.55s`。
- 补丁格式检查：`git diff --check` 通过。
- 真实 ai-pixel 稳定回合探针：后两次调用均读取 `5,888 / 6,497` token，约 `90.6%`。
- 静态语义审计提示词已增至约 1,320 token，但该端点在三次探针中未返回缓存明细；当前应标记为“未知”，不能宣称命中或失败。

## 后续验证建议

下一轮完整三模型长测应直接比较 `by_family` 和 `by_operation`，重点观察：

1. `gm-post-*` 的用户层稳定前缀是否在同一工具循环的第二次调用开始命中。
2. `ground-reply` 与 `ground-tool` 是否开始返回缓存明细；若始终不返回，需区分供应商不报告与缓存前缀仍小于门槛。
3. 各阶段的 `base_prefix_variants` 是否维持在预期范围，避免把每轮动态内容重新混入系统前缀。
4. 优化前后应同时比较 token 成本、P50/P95 延迟和工具循环次数，不能只追求读取比例。

## 2026-08-07 跨消息前缀优化

上一轮只充分利用了同一工具事务内的后续调用。本轮进一步调整核心 GM 的用户消息布局：

1. 稳定的工具定义放在权威状态之前。
2. 权威状态放在当前消息、近期聊天和工具历史之前。
3. 用户消息设置两层断点：工具定义结束、权威状态结束。
4. 与两层系统断点合计保持四个显式断点，不超过当前网关兼容范围。

这样即使一次规则行动改变了战役状态，下一条消息仍可复用工具定义前缀；若状态没有变化，则继续复用“工具定义＋权威状态”的更长前缀。回归测试明确验证了前一种状态变化时工具前缀指纹不变、后一层状态前缀随真实状态变化而失效，不会因追求缓存而读取旧状态。

同时，场次准备、场次契约可达性审查、旧战役导入、长测场次进度审计和 JSON 协议语法修复均已接入统一缓存构造器。生产调用中不再留下已知的无标记 LLM 旁路。

### 三模型短矩阵

测试产物：`outputs/kariba_first_session/20260807_114339`。三个模型并发运行同一段 20 轮桌面流程；该短测用于缓存验证，未要求在 20 轮内完成整场故事，因此 `passed=false` 不代表功能回归。

| 模型 | 可缓存调用 | 返回缓存明细 | 已知命中 | 保守总体读取率 | 已报告调用读取率 |
| --- | ---: | ---: | ---: | ---: | ---: |
| Luna | 62 | 26 | 26 | 29.16% | 61.32% |
| Terra | 60 | 23 | 23 | 26.13% | 61.02% |
| DeepSeek V4 Flash | 85 | 88* | 80 | 59.85% | 59.85% |

\* DeepSeek 的用量明细还包含少量未标记的语法修复调用，因此“返回缓存明细”可高于“可缓存调用”；该旁路已在本轮测试后补齐缓存标记。

与 2026-08-06 长测的保守总体读取率相比，Terra 从 `20.94%` 升至 `26.13%`，DeepSeek 从 `47.55%` 升至 `59.85%`。Luna 仅有 26/62 次可缓存调用返回缓存明细，保守分母会把其余未知调用按零读取计算，因此 `29.16%` 不能与旧值 `32.28%` 直接判定升降；在供应商实际报告的调用中为 `61.32%`。

核心 GM 的工具后续循环最能验证长前缀：Luna `gm-post-scene` 的已报告读取率为 `95.26%`，Terra 为 `93.12%`。首次决策仍需要携带每轮不同的状态与消息，已报告读取率约为 Luna `34.65%`、Terra `38.13%`、DeepSeek `54.00%`，这是下一阶段若要继续提升时应关注的部分。

进一步提升不能靠增加断点，而应把权威状态显式拆成“稳定资料”和“易变现场状态”。这会触及状态摘要契约，必须确保真实变更立即使对应前缀失效；在完成状态字段稳定性分类前，不应为了更高数字冒险缓存可能过期的事实。

追加验证：`2024 passed in 19.24s`。
