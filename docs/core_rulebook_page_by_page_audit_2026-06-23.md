## 总结

FU-GM 已经不是“规则玩具”，而是一个能真实支撑群聊跑团的核心框架：检定、命刻、羁绊、冲突轮转、伤害相性、异常状态、0 HP、休息、旅行、地下城、奖励、Session 0、角色创建、记忆、日志、HTTP 服务、AstrBot 薄插件和 GM 审计面板都已经成型。

但它距离“完整对照核心规则书的长期成品”仍有几个明显缺口：

- 职业技能、英雄技能、NPC 技能和装备特效的“知道规则”多于“自动结算”，很多仍是 `reference_only` 或 prompt 提醒。
- 英雄技能和部分提示词仍有旧译名或旧内部名，例如“奥术回响、嵌合术精通、大口袋、卸甲真言、重唱、我算到了”等应改为当前规则书主名，旧名只保留为输入别名。
- Action Brain、Session 0 facilitator 和消息仲裁仍有不少关键词兜底逻辑，主线已能用 LLM 语义路由，但失败回退和会话门仍偏生硬。
- `interceptor.py`、`http_server.py`、`action_brain.py` 过大，已经进入“能跑但难改”的阶段，应拆成更小的规则包、HTTP handler 和语义路由器。
- 旧审计文档和 Roadmap 已落后于当前仓库，部分“缺失项”其实已实现，部分测试基线仍写 362/441。

2026-06-24 更新：已补可选规则默认关闭/显式启用的战役开关、审计面板展示和运行时上下文注入；已修正【防御精通】只有装备盾牌或职业限定防具时才减伤，并支持装备换皮模板；已去掉第零章启发式里的默认地点污染，只有玩家明确命名或明确描述的地点才会写入世界表。

## 高优先级问题

### P0：官方术语与展示名未完全统一

当前角色/技能库已经能识别正确职业名，但仍有旧译名作为主显示名散落在提示词、英雄技能库、进度管理和文档里。最容易影响用户体验的是英雄技能主名：

| 当前风险显示 | 应优先显示 | 处理建议 |
|---|---|---|
| 奥术回响 | 奥灵共鸣 | 将官方名设为 canonical，旧名保留 alias。 |
| 嵌合术精通 | 拟兽系精通 | 同上。 |
| 大口袋 | 深藏不露 | 同上。 |
| 卸甲真言 | 缴械雄辩 | 同上。 |
| 重唱 | 复诵 | 同上。 |
| 希望 | 重燃希望 | 同上。 |
| 我算到了 | 不出所料！ | 同上。 |
| 堡垒 | 坚强壁垒 | 同上。 |
| 不破之人 | 坚不可摧 | 同上。 |
| 风暴击 | 疾风连打 | 同上。 |
| 强力咒语 | 强效法术 | 同上。 |

这不是纯文本洁癖：角色创建、升级、GM 回答“我能选什么技能”时，如果主名错，玩家会以为规则库还是旧版。

### P0：技能覆盖仍是“知道很多，自动结算不够”

当前技能库统计：

| 类型 | 数量 |
|---|---:|
| 职业技能 | 75 |
| 英雄技能 | 31 |
| NPC 技能 | 16 |
| `hard_rule` | 25 |
| `passive_hard` | 33 |
| `gm_judgement` | 12 |
| `reference_only` | 52 |

优先应从 `reference_only` 中挑出明显可机械结算的技能，升级为被动监听或硬规则动作。例如：

- 职业被动/触发：摄能为食、痛楚、身负黑血、黑暗之心、苦痛教训、天灾骤降、魔法炮击、以械引咒、灵智回流、幸运七、肾上腺素、狂暴、不屈意志、保镖、双盾战士、知识就是力量、予以信任、巧舌如簧、阴狠手段、闪避、疾速身法、鹰眼、治愈之力、法术支援、应急用品、药剂雨、充足补给、宝物猎人。
- NPC 高频技能：飞行、反应、特殊攻击、施法者、最后一搏、异常状态免疫、强化伤害、强化防御、强化先攻。
- 英雄技能：奥灵共鸣、拟兽系精通、深藏不露、缴械雄辩、复诵、重燃希望、不出所料！、坚强壁垒、坚不可摧、技术升级、疾风连打、影逝。

建议做法不是一次性把全部技能写死，而是建立统一触发点：`on_check_after_roll`、`on_attack_before_damage`、`on_damage_after_affinity`、`on_scene_start`、`on_conflict_start`、`on_round_start`、`on_rest`、`on_travel_roll`、`on_clock_progress`。技能先注册到触发点，LLM 仍负责描述创意。

### P0：关键词兜底仍会让 GM 表现生硬

主线 Action Brain 已支持 LLM 语义决策，但仓库里仍存在关键词 fallback：

- `action_brain.py` 仍有职业/仪式/主题判断的关键词分支。
- `message_arbiter.py` 仍有跑团接管、角色创建和规则询问关键词。
- `session_zero_facilitator.py` 仍有大量正则提取角色字段。

这类兜底可以保留，但不应是正常在线体验的第一层。建议改成三层：

1. 快速本地判定只负责明显系统命令、健康检查、存档/读档等低歧义功能。
2. 低成本 LLM Router 负责“是否需要 GM 回复、是不是跑团动作、是不是玩家间讨论、该不该沉默”。
3. Heuristic fallback 只在 LLM 不可用或超时时启用，并在审计日志明确标记 `fallback_reason`。

### P0：旧审计文档和 Roadmap 会误导下一轮开发

`docs/core_rules_33_109_audit.md` 和 `docs/core_rulebook_full_test_flow_and_audit.md` 中仍保留 Windows 路径、旧测试基线和已过期缺口。它们不应删除，因为有历史价值；但需要在开头加“已被本文件 supersede”的提示，或者拆出一个 `docs/audits/` 目录按日期归档。

### P1：核心生物图鉴已录入，但没真正“会打”

`core_bestiary.py` 已有 56 个生物条目，结构化程度不错。问题在于很多“其他行动/特性规则/法术”仍是文本，NPCDirector 和冲突结算并不总能把它们变成真实战斗行为。

建议优先硬化以下特性：

- 飞行与弱点落地。
- 多重攻击。
- 针对魔防的攻击。
- 施加异常状态。
- HP 归零触发最后一搏。
- 危机状态改变相性或攻击。
- 召唤增援与轮末环境效果。
- 蓄力攻击的公开预告。

### P1：稀有物品与自定义装备还需要 builder

项目已录入装备库，且支持装备效果落地的一部分。但规则书强调装备可按角色概念换皮，稀有物品也可设计。当前最缺的是“规则安全的自定义装备流程”：

- 选择基础类别和价格层级。
- 选择命中/伤害公式或防御基线。
- 选择 0-1 个主要特效，检查是否复制职业技能或破坏低等级平衡。
- 记录叙事外观和数值本体的映射，例如“手里剑 = 投掷卡牌”。
- 需要团桌同意时，记录同意状态。

### P1：仪表盘要继续变成“GM 看得懂的规则审计面板”

当前 `/dashboard` 已能看不少状态，但下一步应更明确展示：

- GM 当前记下了哪些世界共识、角色草稿、界限/帷幕、队伍主题。
- 最近一轮 Action Brain 选择了什么动作、为什么回复或沉默。
- 当前场景类型、冲突轮次、行动者、反应窗口、活跃命刻、敌人危机和相性公开状态。
- 哪些规则是硬结算，哪些是 LLM 叙事判断，哪些是 fallback。

## 不建议硬编码的部分

以下内容规则书本身也鼓励 GM 判断，FU-GM 不应为了“自动化”而过度限制 LLM：

- 是否需要战斗、地下城或检定。
- 成功但有代价的具体代价。
- 反派具体动机、战术和逃跑时机。
- 地下城的美学、谜题解法和路线细节。
- 神器效果的世界级后果。
- Boss 是否多部件、多阶段、固定模式。
- 玩家角色装备的叙事外观。

比较好的边界仍是：LLM 决定创意和戏剧方向，Python 负责不能出错的数值、资源、合法性、时机和可审计日志。

## 建议执行顺序

1. **官方术语清理**：先把英雄技能主名、prompt 展示名、文档旧名改干净，旧名只保留 alias。
2. **技能触发点系统**：把最常见被动/触发技能迁入统一 hook，不要继续在拦截器里堆 if。
3. **语义 Router**：让“要不要回复/是不是玩家间讨论/是不是跑团动作”先过低成本 LLM，关键词只做断网兜底。
4. **战斗审计面板**：把轮次、行动者、命刻、反应窗口、敌人公开信息做成 GM 一眼能看的状态。
5. **NPC 特性硬化**：先处理飞行、多重攻击、异常、危机效果、最后一搏、蓄力和增援。
6. **自定义装备 builder**：补角色概念换皮、稀有物品设计和团桌同意流程。
7. **拆分大文件**：把 `interceptor.py`、`http_server.py`、`action_brain.py` 拆出按领域组织的子模块。
8. **审计文档归档**：旧审计文件标记历史版本，Roadmap 改为引用本次 2026-06-23 审计。
